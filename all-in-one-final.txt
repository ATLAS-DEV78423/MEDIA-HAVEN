PART 1 - HOW EVERYTHING WORKS

1.1 THE ONE-SENTENCE MENTAL MODEL
----------------------------------

MEDIA_HAVEN turns a spare Windows laptop connected to a TV into a local media
appliance: you point it at folders you already own, it indexes and presents them
in a full-screen TV-style interface, and it plays them on that same machine -
with no account, no cloud, no subscription and no deletion of your source files.

Everything that DECIDES, STORES, AUTHORISES or PARSES UNTRUSTED BYTES runs inside
a mandatory Docker boundary. Only the final step - turning already-authorised
bytes into pixels and sound - runs on the Windows host.

1.2 SYSTEM SHAPE
-----------------

  Windows 11 laptop / TV via HDMI
  +--------------------------------------------------------------------------+
  | Windows host                                                             |
  |   Tauri 2 shell                                                          |
  |    +-- React 19 / TypeScript UI (WebView2), full-screen TV interface     |
  |    +-- Named product commands (validated, typed; no Docker access)       |
  |    +-- Runtime supervisor (starts/stops only the containers it owns)     |
  |    +-- Windows playback component (mpv via JSON IPC - host-side)         |
  |               |                                                         |
  |               |  one host/container API boundary                         |
  |               |  loopback only, per-install bearer token + HMAC-SHA256   |
  +---------------+----------------------------------------------------------+
                  |
                  v
  +--------------------------------------------------------------------------+
  | Required Docker / Compose workspace (internal; invisible to the user)    |
  |   core  - Rust backend: product rules, API, SQLite, jobs, storage policy |
  |   probe - isolated, networkless media inspection (only untrusted parser) |
  +---------------+----------------------------------------------------------+
                  |
                  |  narrowly selected, per-root, READ-ONLY mounts
                  v
      user-selected original media folders (never modified by the app)

Containers are an internal implementation detail. There is exactly ONE product
surface: one window, one navigation model, one library. The user never sees a
container dashboard, a media-server UI, or a terminal.

1.3 THE DECIDING / PIXELS SPLIT
--------------------------------

This is the architectural idea that explains every other choice.

Runs in Docker `core` (the authority):
  - Library records, watch history, resume positions, queue and watchlist
  - All product policy: what is playable, what is deletable, what is verified
  - SQLite persistence, migrations, storage budgets and job orchestration
  - The signed HTTP API consumed by the UI

Runs in Docker `probe` (the quarantine):
  - ffprobe metadata extraction, thumbnails and trickplay generation
  - The ONLY component that opens untrusted media bytes
  - Distinct non-root UID, read-only root filesystem, size-capped tmpfs,
    no credentials, no database handle, no gateway and no outbound network

Runs on the Windows host (the presentation):
  - Native window, compositor, input and lifecycle
  - The playback engine: the GPU, audio endpoint and vsync exist only here;
    WSL2 offers no cross-vendor hardware video-decode path (ADR-0002)
  - The supervisor that drives the Docker CLI inside the WSL2 distro

Why this matters: if the UI is tricked into displaying something, the backend
has already validated it. The frontend never enforces a security rule, never
computes completion, never decides what may be deleted, and never receives a
raw filesystem path it could act on.

1.4 STARTUP, SHUTDOWN AND FAILURE BEHAVIOUR
-------------------------------------------

Startup:
  1. Read and validate configuration. On failure: quarantine, load defaults,
     warn, continue.
  2. Open SQLite; take a backup before pending migrations; on failure enter
     recovery state.
  3. Reconcile durable state through the required backend when ready.
  4. Detect the supported Docker-compatible runtime read-only. If absent or
     unhealthy: keep the UI available in recovery mode; backend-dependent
     features stay unavailable. There is NO host-side backend fallback.
  5. Start the workspace only through the approved supervisor lifecycle.

Shutdown:
  1. Persist playback position and queue state transactionally.
  2. Stop services this session started, in reverse order, with a bounded
     timeout. The supervisor uses `compose stop`, never `compose down`, so a
     mistaken exit cannot remove a volume.
  3. Close the database cleanly, flush logs, exit with no orphaned children.

Failure handling (designed):
  Corrupt config       -> quarantine, defaults, warn
  Failed migration     -> roll back, keep backup, recovery state, no data loss
  Player crash         -> surface error, offer retry, never mark complete
  Runtime unavailable  -> recovery UI, backend features off, no bypass
  Disk full            -> refuse the write, keep prior state intact, warn
  Power loss           -> recover to last consistent state on next start

There is no autostart service. A media application has no business running when
nobody is watching.

1.5 DATA FLOWS
---------------

(a) First run / preflight
    A read-only PowerShell script reports Windows edition/build, architecture,
    RAM, CPU, GPU, free disk, virtualisation capability, Docker/WSL2 presence
    and networking mode, WSL2 mirrored-mode blocking, shared-runtime detection,
    port availability, WebView2 presence and existing app data. It installs
    nothing, enables no Windows feature, edits no firewall rule and never asks
    for administrator rights. Nothing is written until the final confirmation.

(b) Library scan
    The user selects specific folders. One root = one read-only bind mount
    (/media/root-0, /media/root-1, ...). Roots that are drive roots, reparse
    points, missing paths, duplicates or nested inside another root are refused
    before any mount is emitted. Paths are containment-checked twice (lexically
    and after canonicalisation); the read-only mount is the third layer.
    Scanning never moves, renames or deletes original media, and never scans
    the whole profile, Desktop, Documents or all drives by default.

(c) Browsing the library
    UI asks for shelves via a typed command -> command validates arguments ->
    application use case queries the repository port -> SQLite adapter runs
    indexed queries -> DTOs are assembled -> UI renders and lazily loads
    artwork. The UI never receives an actionable filesystem path.

(d) Playback, resume and completion
    The backend remains the authority for what may play. The host resolves the
    playback source from the media id only - no path or token is placed in the
    renderer (ADR-0015). Resume checkpoints are persisted. A single seek-to-end
    event does not mark an item watched; completion uses multi-signal rules and
    preserves progress on crash. Stopping early never triggers deletion.

(e) Acquisition and rolling two-episode buffer (shipped code; live run NOT RUN)
    For lawfully sourced media only: the operator attaches a magnet or .torrent
    to an item on its Details screen (ADR-0021). A qBittorrent sandbox runs on
    an egress-only Docker network with no published port; its control API is
    loopback-only and uses secret-store credentials. A verified download is
    playable only when it is tied to a media_id AND passes both the file
    inspection probe and a Windows Defender (MpCmdRun) gate. A NULL
    verification is never treated as an allow. While an episode plays, the next
    two episodes are prepared in the background under a 20 GiB cap. No tracker,
    indexer or catalogue is bundled.

(f) Cleanup (fail-safe by design)
    1. UI requests a PREVIEW.
    2. Backend enumerates candidates and applies exclusions: source media,
       currently playing, unfinished, unverified, outside root.
    3. UI shows exact paths and counts.
    4. User confirms explicitly.
    5. An audit event is written; the file is staged to managed trash and
       verified. For downloaded media, deletion is delegated to qBittorrent,
       not performed by `core` (which only has a read-only download mount).
    6. A zero-file result is reported as `failed`, never as success.
    There is no code path from "watched" to "deleted" that skips these steps.

1.6 SECURITY AND PRIVACY MODEL
-------------------------------

Local-first by construction:
  - No account, no subscription, no telemetry, no mandatory paid API.
  - No library data leaves the machine without explicit opt-in.
  - One loopback-only API port with a per-install random token and HMAC
    request signing (ADR-0005). No cookies, no permissive CORS.
  - Docker socket is never mounted into a workload container; no privileged
    containers; all Linux capabilities dropped; no-new-privileges enforced.
  - Distinct non-root UIDs for core and probe; read-only root filesystems;
    explicit tmpfs and named volumes; CPU/memory/PID limits.
  - WSL2 must stay in NAT networking mode. Mirrored mode is a preflight failure
    because it would make the published port reachable from the LAN.
  - Secrets live in Windows Credential Manager, never in source, logs or DTOs.
  - Diagnostic exports redact tokens, passwords, private URLs and personal
    paths. Media is never executed, and file type is not trusted from the
    extension alone.

Honest limits (documented, not hidden):
  - Docker is a process/filesystem boundary, not a security guarantee.
  - A WSL2 kernel exploit defeats the container boundary.
  - The WSL2 filesystem is readable and writable from Windows via \\wsl$, so a
    named volume is not a secret store and is not confidential against the
    same Windows user. No secret is stored there.
  - AppArmor is NOT available on the WSL2 kernel (observed). Seccomp and cgroup
    namespaces remain; probe's networkless design carries the weight.
  - There is no kernel-enforced storage quota on volumes; budgets are enforced
    in application policy instead.

Optional external data (all off by default):
  - Local NFO sidecars are read beside media. TMDB is the primary network
    provider when the operator opts in (ADR-0011).
  - Offline IMDb ratings/age ratings read operator-supplied TSVs locally
    (ADR-0022, Proposed). Zero file reads when off. The only lookup key is an
    IMDb id; no path, folder name or library content is sent.
  - OMDb age ratings are off by default and unwired in this build; enabling
    later requires an operator-supplied key and its own ADR.
  - In the current build the IMDb and OMDb switches are visibly disabled and
    labelled "Not available" - no backend command exists to flip them.

2.3 WHAT MAKES MEDIA_HAVEN DIFFERENT
-------------------------------------

These are deliberate design commitments, not marketing claims. Each one has a
concrete implementation or an ADR behind it.

  1. LOCAL-FIRST, NOT CLOUD-FIRST
     Your library, watch history and preferences stay on your machine. No
     account, no sync, no telemetry, no device registration.

  2. NO AI AT RUNTIME
     AI may help build and set up the product. After setup the application needs
     no AI model, API key or agent. It works fully offline (Development.md #1.3).

  3. A REAL TRUST BOUNDARY FOR UNTRUSTED FILES
     File-format parsers are the highest-risk code in any media app. Only `probe`
     opens untrusted bytes, with no credentials, no database, no network and a
     throwaway filesystem. A compromise has nowhere to go.

  4. READ-ONLY BY DEFAULT, EVERYWHERE
     Your original folders are mounted :ro into containers. A path-traversal bug
     in the backend can at worst disclose files inside a root you chose - it
     cannot damage your library. The app never deletes source media.

  5. DESTRUCTIVE ACTIONS REQUIRE A PREVIEW AND A HUMAN
     Cleanup enumerates exact paths and counts, shows them, waits for explicit
     confirmation, stages to trash, writes an audit event and verifies. A zero
     deletion is reported as a failure. There is no watched-to-deleted shortcut.

  6. FAIL-CLOSED DOWNLOADED-MEDIA GATES
     A downloaded file is playable only when tied to a media_id AND both the
     probe and Windows Defender report Clean. Missing verification is a denial,
     never an implicit allow.

  7. CONTENT-SOURCE NEUTRAL
     No bundled trackers, indexers, catalogues or "where to download" guidance.
     The operator supplies the source; MEDIA_HAVEN manages what they lawfully
     have. The proposed search variant (ADR-0024) still requires an
     operator-supplied endpoint and an operator confirmation.

  8. INFRASTRUCTURE YOU NEVER SEE
     Docker is mandatory but completely hidden. No second dashboard, no terminal
     commands, no container concepts in the UI. The supervisor starts and stops
     only what it owns, and uses `stop` instead of `down` to protect volumes.

  9. INDEPENDENT FROM PROPRIETARY RUNTIME LICENCES
     The proposed runtime is Docker Engine in a dedicated WSL2 distro rather
     than Docker Desktop, avoiding a paid-subscription cliff and an unrelated
     shared daemon. (Distribution is Proposed; the mandatory boundary is accepted.)

 10. TV DISTANCE IS A FIRST-CLASS REQUIREMENT
     No essential text below 16 CSS px in TV mode, deterministic spatial focus,
     tabular numerals for times, focus that never relies on colour alone,
     reduced-motion support, and no autoplaying trailers on focus.

 11. HONEST REPORTING AS A CULTURE
     NOT RUN is a distinct result from PASS. An unexecuted plan stays a plan; a
     Proposed ADR is never treated as approved. progress.md records what was
     actually observed.

 12. SMALL, EXPLAINABLE WORKSPACE
     Two containers, each with one job. SQLite is a file, not a network service.
     Playback stays on the host for GPU/audio/vsync reasons. Every extra service
     needs a measured need and an ADR.

2.4 WHY CHOOSE MEDIA_HAVEN
---------------------------

  If you want a streaming service -> this is the opposite: it is your own
  appliance for media you already own, with no account and no monthly fee.

  If you want a general media server -> MEDIA_HAVEN deliberately does one thing:
  a single, excellent, couch-usable local experience on the laptop plugged into
  your TV. No LAN streaming, no phone app, no multi-user server; those are
  deferred until the local appliance is dependable.

  If you have been assembling scripts and containers yourself -> the hard parts
  are already decided and documented: safe roots, read-only mounts, per-install
  credentials, HMAC signing, fail-closed verification, preview-before-delete,
  bounded cleanup and redacted diagnostics.

  If you care about privacy -> there is no telemetry path by default, no
  mandatory provider, and the optional ones disclose exactly what leaves the
  machine (title/year for search; an IMDb id for ratings).

  If you care about your files -> the application can remove a library root
  without deleting a single original file. Cleanup never touches source media,
  unfinished items, currently playing items or unverified downloads.

  If you care about maintainability -> one codebase, inward-only dependencies,
  a frozen typed command contract, contract-drift guards in CI, and ADRs that
  record why each boundary exists.

  The honest caveat: this is a prototype. Choose it if you want to follow or
  contribute to a carefully engineered local-first media appliance. Do not
  choose it today if you require a verified, supported, signed, one-click
  consumer product - those gates are still open.

2.5 DESIGN AND ACCESSIBILITY COMMITMENTS
-----------------------------------------

  - Near-black ground, centred floating glass navigation, full-bleed cinematic
    hero, landscape Up Next cards and quiet surfaces so artwork carries colour.
  - Tokens only: no literal colour or spacing outside styles/tokens.css,
    enforced in CI by `npm run check:tokens` (66 files, 0 violations observed).
  - Motion is a signal: focus ~140 ms, overlays ~180 ms, hero ~240 ms;
    prefers-reduced-motion zeroes non-essential motion; nothing autoplays on
    focus.
  - Exactly one focused element; deterministic spatial focus; shelf edge
    clamping; column preservation between shelves; Escape unwinds one overlay
    level and restores focus to the originating element.
  - WCAG AA contrast for text over actual rendered artwork; focus always
    visible and never colour-only; complete keyboard-only path on every screen.
  - Full-bleed TV layout plus laptop and narrow-window breakpoints; no per-screen
    colour or spacing inventions.

3.1 HARD REQUIREMENTS
----------------------

  - Windows 11 x64. Windows 10 x64 and ARM64 are NOT claimed until tested
    (roadmap O-02). The preflight reports what it finds; below the supported
    build it warns rather than silently pretending support.
  - A Docker Engine-compatible runtime for any backend-dependent feature. The
    backend and media-inspection workloads run in containers; there is no
    host-side backend fallback. The app detects the runtime read-only and asks
    before using an existing shared engine. It never silently installs one.
  - WSL2 in its default NAT networking mode. A mirrored .wslconfig is a blocking
    preflight condition because it would expose the API port to the LAN.
  - WebView2 (present on Windows 11; the preflight gives an actionable message
    with the official installer link if missing).
  - Enough RAM to carry Windows + the WSL2 VM + core + probe + playback. 8 GB is
    the entry CANDIDATE; 4 GB is explicitly NOT a support target.
  - Free disk space on the drive chosen for managed storage and on the media
    drive. Storage budgets are enforced in application policy.
  - Media you own or are authorised to use. For any download feature, you must
    supply your own lawful source; nothing is bundled.

3.2 RECOMMENDED HARDWARE
-------------------------

  Tier                RAM       Status (all UNTESTED as support claims)
  ------------------  --------  --------------------------------------------
  Minimum experiment  4 GB      Not a support target
  Entry               8 GB      Candidate: library + playback; optional

3.3 WHAT YOU MUST PROVIDE
--------------------------

  - One or more specific media folders. The app will not scan your whole
    profile, Desktop, Documents or all drives by default.
  - A managed-storage location for app data, staging, cache and (if used)
    downloaded media. It may be a different drive.
  - Explicit consent before any host change: runtime provisioning, WSL2 or
    virtualisation enablement, administrator elevation, firewall changes, or
    reuse of an existing shared container engine. Setup will not do these
    silently; declining is always a clean abort.
  - A human decision on Proposed ADRs before their features are relied on
    (IMDb ADR-0022, TMDB artwork ADR-0023, source discovery ADR-0024).
  - For building from source: Node >= 22 with npm, Rust 1.99.0 with rustfmt and
    clippy, the local Tauri CLI, and approved network access for `npm ci`.

3.4 WHAT YOU MUST APPROVE
--------------------------

  - The final setup review: exactly what will be created, where, and which
    runtime/workspace changes will be made. Nothing is written before this.
  - The first cleanup and any change to deletion policy.
  - Removal of app data on uninstall (a separate confirmation from removing
    the application only).
  - Any optional provider: there is no default-on network or download feature.

3.5 WHAT WE EXPLICITLY DO NOT REQUIRE

3.6 YOUR RESPONSIBILITIES

4.1 PATH A - END-USER INSTALLER (INTENDED FLOW; NOT YET PUBLISHED)
------------------------------------------------------------------

STATUS: A real unsigned NSIS installer was BUILT and checksummed locally on
2026-11-21 (v0.1.0, x64, ~3.60 MiB, identifier com.mediahaven.desktop). It is
gitignored, NOT published as a GitHub Release, and has NOT been tested on a
clean VM. The steps below describe the intended flow, not a verified consumer
experience. No installer is available to download from this repository today.

When an installer is published, the steps will be:

  1. Obtain the installer and its SHA256SUMS.txt from the official release
     source. Do not accept a checksum relayed through the same channel as the
     binary.

  2. Verify the file on Windows:

       powershell -NoProfile -Command "Get-FileHash -Algorithm SHA256 .\MEDIA_HAVEN_0.1.0_x64-setup.exe"

     Compare the lowercase hash with the line for that filename in
     SHA256SUMS.txt. `certutil -hashfile <file> SHA256` also works.

  3. Run the installer. It is per-user (NSIS currentUser): it does not require
     administrator rights and does not install or enable system software.

  4. Expect a SmartScreen "Windows protected your PC" / "unknown publisher"
     warning on first run. This is expected for the unsigned v1 build. The
     published guidance is: verify the checksum, then More Info > Run anyway.
     Do not disable Defender or SmartScreen to make installation easier.

  5. Complete the guided first-run setup described in section 4.3.

  6. Back up the database and configuration before any update. Updates preserve
     settings and queue and never overwrite user media.

4.2 PATH B - RUN FROM SOURCE TODAY (VERIFIED CONTRIBUTOR PATH)
---------------------------------------------------------------

This is the path that works in this checkout now. Commands are run from the
repository root unless stated. It requires Node >= 22, Rust 1.99.0 and approved

  Step 1 - Read-only environment check (changes nothing):

    powershell -NoProfile -ExecutionPolicy Bypass -File scripts/windows/preflight.ps1

4.3 THE NINE-STEP FIRST-RUN EXPERIENCE
---------------------------------------

  1. WELCOME - what the app does and what it will never do: no uploads, no
     deletion of your files, no account.
  2. COMPATIBILITY SUMMARY - preflight results in plain language, grouped as
     ready / recommended / needs attention.
  3. MEDIA FOLDERS - pick one or more folders; the app reports how many files
     were found. Nothing is read until you confirm.
  4. MANAGED STORAGE - choose where downloads, staging and trash live, with
     free-space validation. May be on a different drive.
  5. REQUIRED BACKEND RUNTIME - a plain-language explanation that the backend
     needs a Docker-compatible runtime, that it runs headlessly with no Docker
     interface, and that your media is never modified. Every prerequisite and
     host change is shown; explicit consent is required. Declining leaves
     backend-dependent features unavailable; there is no fallback.
  6. OPTIONAL SERVICES - only separately approved providers are listed.
  7. REVIEW - one summary of exactly what will be created, where, and which
     runtime/workspace changes will occur.
  8. CONFIRM - an explicit action. Nothing is written before this point.
  9. DONE - the library opens only when the required backend is ready;
     otherwise you get recovery guidance.

  Setup never: installs software, enables WSL2/Hyper-V/virtualisation or any
  Windows feature, requests administrator rights, changes firewall/proxy/DNS,
  scans broad personal folders, writes configuration before final confirmation,
  or pretends the required runtime is optional.

4.4 ADDING MEDIA AND STARTING TO WATCH
---------------------------------------

  1. Open Settings > Library folders (or the Setup screen on first run) and add
     a specific folder containing your movies or TV shows.
  2. Wait for the scan. Only selected folders are read; originals are not
     changed. Missing/offline files are reported, not silently dropped.
  3. Go to Home. Continue Watching, Recently Added, Up Next and a deterministic
     Recommendation shelf are built from local data.
  4. Browse Movies or TV Shows, or use Search (local library first).
  5. Open a Details view to see metadata, season chips, episode progress and -
     for authorized media you supply - the Source field.
  6. Press Play. Use arrows, Enter, Escape, mouse or a mapped remote/controller.
     Escape unwinds one overlay level and restores focus.
  7. Progress and resume position are saved. Stopping early keeps your place.
  8. Add items to Watchlist from any card or Details view. It keeps your order,
     works offline, and never deletes media.

  Honest note: in the current prototype the player displays artwork with a
  simulated 4x clock and labels itself "Playback preview". Real video playback,
  live provider artwork and live downloads are NOT RUN. Library scanning,
  persistence, search, watchlist, profiles, sessions and checkpoints are real.

4.6 TROUBLESHOOTING AND RECOVERY
--------------------------------

  Symptom: backend-dependent features unavailable
    The runtime is absent or unhealthy. The UI stays available for diagnostics;
    use preflight to see which check failed. There is no host fallback.

  Symptom: mirrored WSL2 networking reported as blocking
    WSL2 mirrored mode makes the instance LAN-reachable. Return to NAT mode.
    Do not work around this check.

  Symptom: a shared Docker engine is detected
    The app reports it and asks before use. A dedicated engine is preferred so
    an unrelated project's `docker compose down` cannot stop our workspace.

  Symptom: port already in use
    Preflight reports availability. Resolve the conflict on loopback; never
    publish the API to the LAN or add a netsh portproxy rule.

  Symptom: config corrupt
    The file is quarantined, defaults are loaded and a warning is shown. The
    quarantined file is kept for inspection.

  Symptom: migration failed
    The migration rolls back, the backup is retained and the app enters
    recovery state. No data is discarded without explicit confirmation.

  Symptom: player crashes
    The error is surfaced with a retry; the item is NOT marked complete and the
    resume position is preserved.

  Symptom: download item not playable
    Both the probe and Windows Defender verifications must be Clean and the item
    must be tied to a media_id. A missing (NULL) verification is a denial.

  Symptom: setup was interrupted
    The next launch detects the incomplete state and offers resume or restart.
    Configuration is never half-applied.

4.7 UNINSTALL
--------------

  The installer offers two distinct choices:

  - REMOVE APPLICATION ONLY (default): removes program files, shortcuts,
    services and scheduled tasks. Keeps the database, config, artwork, logs and
    any managed media so a reinstall resumes where you left off.
  - REMOVE APPLICATION AND MANAGED DATA: additionally removes app data. It shows
    the exact paths and requires a separate explicit confirmation.

  It never removes your source media or a folder you selected as a library root.
  It never uninstalls WSL2, Docker Desktop or a shared runtime that other
  applications may depend on. If MEDIA_HAVEN owns a dedicated distro or volume,
  removing it is a separate confirmed action after a verified backup.

  NOTE: uninstall behaviour against the built installer is NOT RUN (P7-02).
