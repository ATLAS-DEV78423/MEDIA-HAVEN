# ADR-0014: Host token storage uses DPAPI, not a Credential Manager entry

- **Status:** Accepted (2026-11-18)
- **Date:** 2026-11-18
- **Deciders:** human partner (accepted 2026-11-18), contributing agent
- **Amends:** ADR-0007 (secret storage mechanism, for the API token only)
- **Related:** ADR-0005, ADR-0007, ADR-0013, plan `2026-11-18-backend-completion.md` (D-7)

## Context

ADR-0007 requires the host-to-container API token to live in **Windows
Credential Manager** with target name `MEDIA_HAVEN/api-token`. Reaching
Credential Manager from Rust means either adding a crate (`keyring`) or calling
Win32 `CredWrite`/`CredRead` through the `windows` crate. A new dependency
requires an ADR and approval, and the plan's D-7 gate asked which mechanism to
use.

The alternatives differ in scope, not just in convenience:

- **DPAPI** (`CryptProtectData`/`CryptUnprotectData`) encrypts a blob under the
  current Windows user's profile. It needs no new crate if the `windows` crate
  is already present, but the result is an opaque file, not a Credential
  Manager entry, and it is not visible or revocable from the Credentials UI.
- **Credential Manager** gives a real, user-visible, revocable entry. It
  requires the `keyring` crate (a new dependency) or hand-written Win32 calls.

## Decision

**The host stores the API token as a DPAPI-protected blob scoped to the current
Windows user, using the `windows` crate.** No new dependency is added for this
purpose.

This amends ADR-0007's *storage mechanism* for the API token. ADR-0007's other
rules stand unchanged and are not weakened:

- no token in the repository, an image, a compose file, a log or a crash report;
- generated by the host with a CSPRNG on first run;
- passed to `core` only as an environment variable set by the supervisor;
- rotation is one action;
- uninstall offers to remove the stored blob;
- access requires the Windows user's session.

Provider API keys are **not** covered by this decision; they remain governed by
ADR-0007 until a task needs them, and will get their own decision if a different
mechanism is wanted.

## Acceptance record

- **2026-11-18 — accepted by the human partner.** Presented with three options
  (DPAPI via the existing `windows` crate, add `keyring`, or defer), the human
  partner chose **DPAPI**. Recorded here by the agent at the human's direction.

## Consequences

Positive: no new dependency, no ADR for a crate, and the token is encrypted at
rest against other Windows users. Fewer moving parts in the supervisor.

Negative, and accepted: the token is not visible in the Credentials UI, so a
user cannot inspect or revoke it there; uninstall must delete the file itself.
DPAPI protection is tied to the user profile — a roaming-profile or machine
transfer does not carry it, and the app must regenerate rather than fail.

Harder: the "rotation is one action" promise now includes rewriting the DPAPI
file and invalidating in-flight requests in the same operation, which A3 must
implement and test.

## Verification required before this is relied upon

- A round-trip test: protect, unprotect, compare.
- A test that a second Windows user (or a copied profile) cannot unprotect the
  blob, reported honestly if it cannot be exercised on this machine.
- A grep test that no token literal reaches disk, logs or the bundle.

## Revisit trigger

The threat model gains a hostile same-user process, or Credential Manager
visibility/revocation becomes a product requirement. Then supersede this ADR
with the `keyring` route.
