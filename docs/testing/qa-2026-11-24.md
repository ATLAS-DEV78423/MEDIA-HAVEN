## 3. Defects found

### D1 — CRITICAL: the running `core` image predates the catalog feature

`POST /host/catalog_wanted_add` returned **HTTP 404** against the running
container. The image `mediahaven-core:local` was built 23 hours earlier
(2026-11-23 18:38) than commit `9e5d5ec` (2026-11-24), which introduced that
route. The `host` command forwards to the route and maps 404 → `NotFound`
("The requested item was not found.").

Effect, exactly as the user described: clicking a poster in Discover, Home, or
an anime/TV card calls `catalogWantedAdd` → 404 → the card never navigates to
Details. **This is the "movies and anime and tv shows don't load when you
click the play button or on their posters" symptom.**

There is no build automation for the container images (`scripts/` and
`.github/workflows/` contain no `docker build` for `core`), so the running
image silently drifts behind the checked-out source. The `core` image was
rebuilt from `infrastructure/containers/Dockerfile.core` and the container
recreated; the route now answers 400 (bad body) instead of 404 (missing).

Verified after the rebuild:
`POST /host/catalog_wanted_add {"title":"Iron Man","year":2008,"kind":"movie"}`
→ **HTTP 200** `{"mediaId":"catalog-movie-473b1e264d9018c8c4b9d2549a159319"}`,
and `library_detail` for that id returns the title.

### D2 — CRITICAL: confirming a magnet never starts a download

`source_set` (the Details screen "Confirm" / "Save source" action) only writes
the source to the `item_sources` table. It never calls the acquisition
orchestrator.

Evidence — the complete set of production callers of `acquire()`:
- `crates/core/src/acquisition.rs:291` — the `add` route (`host/acquisition_add`),
  reachable only from the **Downloads page** "Add source" dialog.
- `crates/core/src/acquisition.rs:876` — the **prefetch** scheduler, which only
  fills the *next two episodes* of a series **already being played**.

Nothing on the Details screen and nothing on the catalog path starts a
download. So a user who picks a title, finds a source and confirms it sees
"Source saved for this item." and then **nothing ever downloads**. This is the
"it's not able to get the magnet link and act on it" symptom.

### D3 — CRITICAL: a confirmed source can never become playable

Even if a download is started by hand from the Downloads page, the file can
never be played, because the *playback* path and the *download* path are two
disconnected stores:

| Concern | Table written by the download path | Table read by playback |
|---|---|---|
| file location | `download_items.file_path`, `file_mappings.file_path` | `media_files.path` (via `media_source_path`) |
| readiness | `download_items.state` / `verification_state` | `media_items.availability_state` |

`media_source_path()` (`crates/persistence/src/sqlite/library_repo.rs:819`)
selects **only** from `media_files`. The acquisition path never inserts a
`media_files` row — the only writer of `media_files` is the library scanner
(`media_replace_for_root`). So `GET /playback_source/:id` returns
`{"path": null}` for every acquired file, and `playback_start` fails with
`MediaMissing`.

Live proof on the fresh container: a wanted catalog item returns
`{"path":null}` from `playback_source`.

### D4 — CRITICAL: the download-root bind is read-only for `core`

`core` is a `read_only: true` container; the only writable mount it gets is
`staging`. The `/downloads` bind is `:ro`. The qB container mounts the same
host directory `:rw`. Any design that expects `core` to *write* into
`/downloads` cannot work; equally, `core` can read `/downloads` but the path
it would need (`/downloads/...`) is not what `media_files` holds.

### D5 — HIGH: qBittorrent WebUI rejects the host's requests (401)

`POST /api/v2/auth/login` from the host to `127.0.0.1:8090` returns **401**
even with the correct password.

This was **not** a password-hash problem, despite the earlier report
suggesting so. Two independent lines of evidence:
- The stored `Password_PBKDF2` matches **standard PBKDF2-HMAC-SHA512,
  100 000 iterations** over the injected token (verified by recomputing the
  hash from the stored salt — it matches byte-for-byte). The Dockerfile's
  generator is therefore correct.
- qB's **own** generated password also fails from the host, and a password
  set *through qB's own API* fails from the host too.

The actual discriminator is the **Host header**. qB validates the `Host`
header against its own listening port:

| Request | Result |
|---|---|
| from host, `Host: 127.0.0.1:8095` (published port) | **401** |
| from host, `Host: 127.0.0.1:8080` (container port) | **204** |
| from host, `Host: qbittorrent:8080` | **401** |
| from inside the container, `Host: 127.0.0.1:8080` | **204** |

`crates/acquisition/src/qbittorrent.rs:121` builds `Host: {address}:{port}`
from the *URL it dialled*, so the client sends the correct port and
`core → qbittorrent:8080` works. Verified live from the `core` container:
`login=204`. The 401 only occurs when a request reaches qB through the
**published host port** (8090), where the `Host` header carries 8090 but qB
listens on 8080.

**Conclusion: the magnet chain is not blocked by qB auth.** The earlier
"E2E blocker" in `docs/testing/e2e-2026-11-24.md` was a mis-diagnosis caused
by testing qB through the wrong port.

### D6 — HIGH: `library_home` was 4–6 s

Measured against the stale container: `library_home` **4200 / 5311 / 5936 /
5068 ms** while every other route was ~800 ms. The route is the only one that
walks series → seasons (`home()` calls `series_detail()` per series row, each
issuing a separate `seasons_for` query — an N+1), plus it builds the full
`MEDIA_COLUMNS` projection for every item.

After rebuilding the image the same route measured **1019 ms** then **754 ms**,
i.e. in line with the other routes. The N+1 remains in the code and will
re-emerge as the library grows; it is called out as **F6** below.

### D7 — MEDIUM: the catalog "unavailable" state is a dead end with no retry

`DiscoverPage` shows "The catalog is unavailable" when the browse fails, with
no way to retry and **no way to keep the last good titles**. The in-flight
work in the tree adds a Retry action, but the *stale browse* case still
replaces the grid with an error. `HomePage` has the same shape.

### D8 — MEDIUM: `catalog_wanted_add` creates a wanted item that can never play

`wanted_add` inserts a `media_items` row with `availability_state='unavailable'`
and **no** `media_files` row — correct as a "wanted" record. But because
`availability()` maps every state that is not `"missing-file"` or `"offline"`
to `Available`, the wanted row reports `availability: {"state":"available"}`
in `library_detail` (observed live), and `playback_start` happily returns a
session for it. The failure then surfaces late, as a media-missing error at
the host, instead of an honest "not downloaded yet" state.

### D9 — LOW: the `Downloads` screen is permanently disabled

`downloads()` in the repository returns a hard-coded
`DownloadsScreen { enabled: false, tasks: vec![], ... }`, so the Downloads
page always shows "Downloads are switched off" and never lists the real
acquisition rows it fetched from `download_status`. The two sources disagree
by construction.

### D10 — LOW: `source_search` results are discarded on the Details screen

`confirmSource` writes the magnet and refreshes the detail, but the shortlist
UI has no "downloading"/"queued" state, so a user who confirms a source gets
no feedback that anything happened — compounded by D2, nothing *does* happen.

### D11 — HIGH: acquisition status was frozen at add time

`AcquisitionState::refresh()` did not exist, and `/host/acquisition_status`
returned the in-memory rows unchanged. A torrent that completed later stayed
`Downloading` at its original percentage forever and was never inspected for
playback. Fixed with a real qB status refresh, SQLite persistence of
state/progress, and inspection persistence on the refresh path. Lifecycle
states owned by cleanup (`playing`, `watched`, `cleanup_pending`) are preserved.

### D12 — CRITICAL: the Defender gate had no production caller

`MpCmdRunScanner` / `defender_scan()` existed with tests, but no production
code ever wrote `download_items.defender_state`. Every acquired file therefore
failed `refuse_unscanned_download()` and could never play. Fixed with two
signed host-only routes (read/record Defender state by media id) and a
pre-play host scan of the resolved Windows path before the backend playback
gate. Library imports (no download row) skip the scan. Unknown state strings
and path-like ids are rejected; no path or scanner output crosses the boundary.

### D13 — HIGH: placeholder acquisition paths were never reconciled

When qB has no file list at add time, `acquire_for_media` persists
`/downloads/{hash}` as a placeholder. The real member names can appear only
later, and nothing updated `download_items.file_path` / `file_mappings`, so
`/playback_source/:id` still pointed at a non-existent file. Fixed by asking
qB for member names during the ready-state refresh and replacing only
auto-created mappings; manual episode mappings are preserved.

### D14 — HIGH: real-world magnets were rejected by the 2048-character cap

The earlier E2E note recorded that 2.2k-character magnets were dropped, but the
cap was still **2048** in all three live validators:
`crates/acquisition/src/orchestrator.rs`,
`crates/app-core/src/domain/media.rs`, and
`apps/desktop/src/pages/Details/MediaDetailsPage.tsx`. A user pasting a
multi-tracker magnet therefore saw "too long or contains invalid characters"
in the UI, and the same source was refused at both Rust boundaries. Fixed by
raising all three caps to **8192** in step, with regression tests using a
2.2k-character magnet at each layer. The unrelated 2048 AniList *poster URL*
cap in `discovery.rs` was deliberately left unchanged.

### D15 — HIGH: every qB call waited for the keep-alive socket to close

During live redeploy, `source_set` timed out at 30 s even though the torrent
was created and the database row was persisted. Direct checks showed qB login
was 204 and its file endpoint was ~1 ms, so the delay was in the hand-written
WebUI client. qB answers with `Connection: keep-alive` and an exact
`Content-Length`, but `exchange()` used `read_to_end()` and waited for qB to
close the idle socket (~9 s). Fixed by parsing the head first and reading only
the declared body length (with read-to-EOF as fallback for responses without a
length). A fake-server regression test now holds the final socket open and
asserts the client returns before the close.

### D16 — HIGH: a duplicate torrent source could not be confirmed twice

After a core restart, confirming the same source again returned HTTP 503. qB
answers a duplicate `torrents/add` with **409 Conflict**; the client treated all
non-2xx responses as a backend failure before it could resolve the existing row
from the info list. Fixed by treating 409 as an idempotent add and continuing
to the existing-row lookup. A fake-server test covers the 409 → info path.

### D17 — MEDIUM: restarts dropped tracked downloads from status

`AcquisitionState` lives only in memory. After recreating `core`, persisted
download rows remained in SQLite but disappeared from `/host/acquisition_status`
and could not be removed through the API. Fixed by loading persisted rows
(`acquisition_rows()`) at startup and restoring them into the tracker, with
repository and orchestrator regression tests. The next status poll reconciles
them against qB.

### D18 — MEDIUM: removal only cleared the in-memory tracker

`POST /host/acquisition_remove` removed the qB task but never deleted the
persisted `download_items` row. After the D17 restart fix this became visible:
a "removed" download reappeared in status on the next restart. Fixed by calling
`download_remove()` on the service after the engine removal succeeds, with a
persistence regression test proving the row is gone.

## 4. Root-cause summary

The user's symptoms have **nine independent causes**, which is why fixing one
did not fix the others:

1. **Stale deployment (D1).** The running backend did not contain the catalog
   feature at all. Every poster click 404'd. → *fixed by rebuilding the image*.
2. **A broken hand-off (D2/D3).** `source_set` records a magnet but never starts
   the acquisition, and the acquisition that *can* be started (Downloads page)
   writes to tables playback never reads. So a confirmed magnet is inert and
   an acquired file is unplayable.
3. **Frozen and incomplete state (D11/D12/D13).** Status polling replayed the
   add-time snapshot, the Defender gate was never invoked, and placeholder
   paths were never replaced. Even a successful download could not be seen as
   ready or pass the pre-play gates.
4. **Missing status honesty (D8/D9/D10) and slow reads (D6).** A wanted item
   claims to be available; the Downloads screen reports itself off; a confirmed
   source gave no on-screen acknowledgement; the home route is 5× slower than
   its siblings.
5. **A contradictory input cap (D14).** An earlier fix had been recorded as
   8192, but the three effective validators still capped sources at 2048, so
   ordinary multi-tracker magnets were refused before acquisition could start.
6. **A transport-level stall (D15).** qB kept its HTTP connection alive after
   sending a complete response; the client waited for EOF, adding ~9 s to
   every acquisition call and causing the first live `source_set` to time out.
7. **A non-idempotent duplicate (D16).** qB's 409 Conflict for an already-held
   torrent was reported as a backend failure instead of resolving the existing
   task, so repeating a confirmation after a restart failed.
8. **Lost in-memory state (D17).** The qB tracker was empty after a restart,
   so persisted downloads vanished from status until re-added.
9. **Non-persistent removal (D18).** A removed task stayed in SQLite and came
   back after the restart fix restored persisted rows.

## 6. NOT RUN / known limitations

- **Real magnet → qBittorrent → probe → Defender → mpv playback.** No lawful
  source was available in this environment, so the end-to-end media path was
  not exercised with a real torrent. The qB *auth* path (204 from `core`) and
  the synthetic-magnet acquisition path **were** proven live; the remaining
  media stages were proven with fakes.
- **Windows Defender scan of a real downloaded file.** `MpCmdRun.exe` is
  present on the host but no real downloaded file existed to scan. The gate
  logic is covered by the fake-scanner tests; the live scan is NOT RUN.
- **Live `probe` container inspection of a real file.** Same reason.
- **Second-machine LAN reachability.** Not re-tested in this pass.
- **Large-library performance.** Only the small fixture library was present.
  The stale-image slowdown was observed and the rebuild helped on that tiny
  dataset, but the N+1 is not fixed and no 10 000-item benchmark was run.
- **AniList / TMDB live catalogue calls** were not repeated; the catalog
  behaviour was exercised against the local backend only.
- **Live checks used synthetic magnets only.** They prove route wiring, qB
  task creation, status refresh, Defender state routes, path resolution and
  restart/removal behaviour, but they did not download or play a real media
  file. No real payload was present for probe or Defender to inspect.
- **Details does not poll live progress.** D10's missing acknowledgement is
  fixed: the confirmed row and manual-source section now say that the download
  started and link to Downloads. The badge does not claim a live percentage;
  Downloads remains the authoritative progress view.
